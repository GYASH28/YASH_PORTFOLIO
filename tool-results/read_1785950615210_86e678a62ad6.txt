    15→## How to use this document
    16→
    17→This document has two purposes:
    18→
    19→1. **Reference audit:** it explains what makes each reference site visually successful, how its structure, motion, typography, interaction, and storytelling work together, and which principles are relevant to Yash Ganesh’s portfolio.
    20→2. **Master implementation prompt:** it gives a coding agent a complete instruction set for transforming the existing website into a polished, original, responsive, animated, production-grade portfolio.
    21→
    22→The goal is **not** to merge four websites into a visual collage. The goal is to extract the strongest underlying principles from all four and create one unmistakably original experience for **Y/G Systems Studio**.
    23→
    24→Some reference behavior is created through dynamic WebGL, custom shaders, hover states, scroll states, and route transitions that cannot be fully represented by static HTML alone. Therefore, the analysis below combines observable page structure, visible interface elements, public project descriptions, award-gallery descriptions, and the design logic implied by the interactions. The final design must be validated by manually using every reference on desktop and mobile before implementation begins.

    28→# PART I — CURRENT WEBSITE AUDIT
    29→
    30→## 1. Existing identity worth preserving
    31→
    32→The current Y/G website already has a stronger conceptual foundation than a typical developer portfolio. It includes:
    33→
    34→- **Y/G — Systems Studio**
    35→- **A Human Signal Inside the Machine**
    36→- **Observe / Question / Build / Improve**
    37→- **Building Useful Futures**
    38→- **Not another AI wrapper. A working product.**
    39→- **Observe → Structure → Engineer → Evolve**
    40→- **Products with a Pulse**
    41→- Product strategy, experience design, AI implementation, and full-stack delivery
    42→- A personal story based around being a young product-focused developer from Pune
    43→- Real products such as Lernio AI, B.R.A.C.E., CampusMate, and Fakhri Mart
    44→
    45→These ideas are strong because they already provide a world, a philosophy, and a visual metaphor. The redesign must expand this system rather than replace it with a generic “creative developer” identity.
    46→
    47→## 2. Current structural strengths
    48→
    49→The current homepage follows a sensible narrative:
    50→
    51→1. Intro / opening
    52→2. Hero and positioning
    53→3. “Not another AI wrapper” statement
    54→4. System methodology
    55→5. Selected work
    56→6. Capabilities
    57→7. About
    58→8. Final CTA
    59→
    60→This overall sequence should remain recognizable because it tells a clear story from identity to process to proof to contact.
    61→
    62→## 3. Current limitations to solve
    63→
    64→The redesign should address the following likely limitations in the present experience:
    65→
    66→### 3.1 Sections feel like separate content blocks
    67→
    68→The current sections are conceptually related, but the visual experience does not always make them feel like one continuous system. The redesign should create visual continuity so that a shape, signal, line, node, or material from one scene transforms into the next.
    69→
    70→### 3.2 The project section relies heavily on screenshots
    71→
    72→Screenshots prove that the products exist, but a portfolio at this level must also communicate what each system does, why it matters, how it works, and what Yash contributed. Each project should have its own miniature world, motion language, and clear case-study entry point.
    73→
    74→### 3.3 Motion needs stronger hierarchy
    75→
    76→Not every element should receive the same type of reveal. The redesigned site needs a motion system with distinct levels:
    77→
    78→- Immediate UI feedback
    79→- Text and component transitions
    80→- Scroll-controlled narrative sequences
    81→- One or two cinematic WebGL moments
    82→- Quiet reading states
    83→
    84→### 3.4 3D should carry meaning
    85→
    86→A generic floating sphere, orb, or particle field would weaken the concept. The 3D system should represent the relationship between human intent, product structure, intelligence, iteration, and engineering.
    87→
    88→### 3.5 Mobile must be separately art-directed
    89→
    90→A complex desktop timeline cannot simply be squeezed into 390 pixels. The mobile site needs its own section choreography, shorter motion paths, touch-safe interactions, simpler scene geometry, and more direct project navigation.
    91→
    92→### 3.6 The site needs more proof and conversion clarity
    93→
    94→The current identity is memorable, but potential collaborators should quickly understand:
    95→
    96→- What Yash builds
    97→- What types of problems he can solve
    98→- Which projects are real and live
    99→- What role he played
   100→- How to contact him
   101→- What kind of collaboration is appropriate
   102→
   103→The redesign must keep the artistic direction while improving trust and clarity.

   109→# 4. OhhMyDesign — Why it feels alive
   110→
   111→## 4.1 Core design idea
   112→
   113→OhhMyDesign turns a studio website into a collection of familiar digital workspaces. Instead of presenting every section as a normal webpage section, it repeatedly borrows the visual language of tools people already understand:
   114→
   115→- Figma frames
   116→- Chat channels
   117→- Project boards
   118→- Review cards
   119→- Live cursors
   120→- File names
   121→- Canvas dimensions
   122→- Pricing controls
   123→- Comment threads
   124→- Status indicators
   125→- Tooltips and tiny system labels
   126→
   127→The site feels good because the interface itself becomes the storytelling device.
   128→
   129→## 4.2 Hero structure
   130→
   131→The hero establishes personality immediately through:
   132→
   133→- Strong availability language
   134→- Live time / timezone details
   135→- Distributed team positioning
   136→- A large, aggressive headline
   137→- A smaller line that acts like a design manifesto
   138→- A project strip or interactive visual area that suggests dragging and exploration
   139→- Direct conversion CTAs
   140→
   141→The important lesson is that the hero does not only look bold. It establishes the studio’s operating style: direct, playful, fast, and impossible to ignore.
   142→
   143→## 4.3 Interface storytelling
   144→
   145→Several sections appear as named digital artifacts, such as:
   146→
   147→- `STATEMENT.TXT`
   148→- `hero.frame`
   149→- `pricing.fig`
   150→- `the-difference.fig`
   151→- `footer.frame`
   152→- Named FAQ frames
   153→
   154→This naming system makes the page feel like the visitor is looking inside an active design process rather than reading a brochure.
   155→
   156→### Why this works
   157→
   158→- It creates continuity across unrelated content.
   159→- It turns labels into personality.
   160→- It makes the site feel authored rather than templated.
   161→- It adds detail without requiring excessive decoration.
   162→- It rewards visitors who notice small things.
   163→
   164→### What to borrow for Y/G
   165→
   166→Use a similar principle, but translate it into Y/G’s engineering language rather than copying Figma file names everywhere. Possible Y/G labels:
   167→
   168→- `SIGNAL_BOOT.log`
   169→- `SYSTEM_MAP.01`
   170→- `WORKFLOW_TRACE`
   171→- `PROJECT_CORE`
   172→- `HUMAN_LAYER`
   173→- `DEPLOYMENT_STATUS`
   174→- `MEMORY_NODE`
   175→- `BUILD_PIPELINE`
   176→
   177→The labels should feel like one coherent operating system, not random developer jargon.
   178→
   179→## 4.4 Work presentation
   180→
   181→The work is introduced early and repeated through moving or draggable visual units. Rather than hiding the portfolio behind a single “Work” page, the site uses projects as visual proof throughout the experience.
   182→
   183→### What makes it effective
   184→
   185→- Project imagery appears before long explanations.
   186→- The visitor immediately sees range.
   187→- Repetition builds credibility.
   188→- Motion creates momentum without requiring full case-study reading.
   189→- Tags quickly establish category and context.
   190→
   191→### Application to Y/G
   192→
   193→The Y/G hero could contain a restrained stream of real product fragments:
   194→
   195→- Lernio lesson nodes
   196→- B.R.A.C.E. voice waveform
   197→- CampusMate QR grid
   198→- Fakhri Mart yarn strands
   199→
   200→These fragments should later become full project scenes, creating recognition and continuity.
   201→
   202→## 4.5 “What’s up” statement section
   203→
   204→OhhMyDesign follows spectacle with a direct statement of what it believes. The typography and file-window framing give the copy importance without requiring a huge paragraph.
   205→
   206→### Lesson
   207→
   208→After a visually intense hero, visitors need a concise section that explains the position in plain language. Y/G already has the perfect concept for this:
   209→
   210→> Not another AI wrapper. A working product.
   211→
   212→This section should become a visual proof of the claim, not only text.
   213→
   214→## 4.6 Process as a chat thread
   215→
   216→The process is expressed as a conversation between the studio and the client:
   217→
   218→1. Subscribe
   219→2. Send the brief
   220→3. Refine
   221→4. Ship
   222→
   223→The process feels fast and human because it is shown through a chat channel with timestamps, file attachments, reactions, and short dialogue.
   224→
   225→### Why this is better than standard process cards
   226→
   227→- It demonstrates communication rather than claiming it.
   228→- It makes the process feel realistic.
   229→- It reduces corporate language.
   230→- It creates an easy scroll narrative.
   231→- It gives motion designers natural opportunities for typing, attachment arrival, reaction, and status transitions.
   232→
   233→### Application to Y/G
   234→
   235→Y/G’s process should not copy a Slack window, but it can demonstrate the lifecycle of a product through a live system trace:
   236→
   237→- A user problem enters as an unstructured signal.
   238→- Research and observations appear.
   239→- The signal becomes a workflow.
   240→- The workflow becomes a prototype.
   241→- The prototype becomes an engineered system.
   242→- The system is deployed.
   243→- Feedback returns and updates the system.
   244→
   245→This would communicate **Observe → Structure → Engineer → Evolve** in a similarly concrete way.
   246→
   247→## 4.7 Horizontal services canvas
   248→
   249→OhhMyDesign presents services as a horizontal canvas rather than ordinary stacked cards. The visitor moves sideways through different service spaces.
   250→
   251→### Why it works
   252→
   253→- It changes the physical rhythm of the page.
   254→- It makes each service feel like a separate workspace.
   255→- It supports wide visual compositions.
   256→- It creates a memorable moment without needing WebGL.
   257→
   258→### Risk
   259→
   260→Horizontal scroll can be frustrating when it hijacks normal scrolling or behaves poorly on mobile.
   261→
   262→### Application to Y/G
   263→
   264→Use a desktop-only pinned system map for capabilities. On mobile, convert it into a vertical accordion or stacked chapter system. Do not preserve horizontal movement merely for consistency.
   265→
   266→## 4.8 Comparison section
   267→
   268→The “same brief, different studio” section uses a comparison-frame metaphor. It creates a decision moment by showing two possible experiences side by side.
   269→
   270→### Application to Y/G
   271→
   272→Use this logic in the “Not another AI wrapper” section:
   273→
   274→**Disconnected AI demo** vs. **Complete working product**
   275→
   276→Compare:
   277→
   278→- Prompt box vs. complete workflow
   279→- Model call vs. model routing
   280→- Stateless reply vs. memory
   281→- Pretty screen vs. edge cases
   282→- Demo data vs. real data
   283→- Prototype vs. deployment
   284→- Feature list vs. actual user value
   285→
   286→The section should visually reorganize the disconnected pieces into a functioning system.
   287→
   288→## 4.9 Testimonials and social proof
   289→
   290→The site presents proof through different native-looking formats:
   291→
   292→- Video-style cards
   293→- Social comments
   294→- Review cards
   295→- Metrics
   296→- Named founders
   297→
   298→### Lesson for Y/G
   299→
   300→Yash may not yet have dozens of client reviews. Do not fabricate them. Use truthful proof instead:
   301→
   302→- Live products
   303→- Repository links
   304→- Product screenshots
   305→- Number of real subjects / lessons / roles only when verified
   306→- Deployment status
   307→- Real client project status
   308→- Short, accurate statements about the purpose and current stage
   309→- College or community use only when true
   310→
   311→Proof does not need to look corporate; it needs to be verifiable.
   312→
   313→## 4.10 Dynamic local CTA
   314→
   315→The site references the time in India and adjusts its closing language accordingly. This makes the page feel live.
   316→
   317→### Application to Y/G
   318→
   319→Use a small live Pune time and availability status in the HUD. Avoid overcomplicated location tracking. A simple client-side local time for Pune is enough.
   320→
   321→## 4.11 Pricing interaction and playful surprise
   322→
   323→The pricing section contains a tactile selection control, while a deliberately useless button creates a playful moment near the end.
   324→
   325→### Lesson
   326→
   327→A premium portfolio benefits from one optional moment that exists purely for delight. It should not interrupt the main journey or hide essential content.
   328→
   329→### Y/G equivalent
   330→
   331→A small “Do not destabilize the core” control could briefly disturb the Signal Core, scramble a few interface readings, and then recover. It should be optional, accessible, and disabled under reduced motion.
   332→
   333→## 4.12 What Y/G should learn from OhhMyDesign
   334→
   335→Borrow:
   336→
   337→- Interface-as-storytelling
   338→- Named system artifacts
   339→- Real-time presence details
   340→- Project proof early in the page
   341→- Process demonstrated through behavior
   342→- Different interaction mechanic for major sections
   343→- Playful microcopy
   344→- One optional surprise
   345→- Strong CTA clarity
   346→
   347→Do not copy:
   348→
   349→- Figma window styling directly
   350→- Their exact headlines or jokes
   351→- Their subscription business structure
   352→- Fake cursor collaboration
   353→- Excessive interface chrome
   354→- Every section being a software mockup

   554→# 6. Ryan Ritzenthaler — Why the portfolio rewards exploration
   555→
   556→## 6.1 Core design idea
   557→
   558→Ryan’s portfolio combines practical project information with playful interaction. Public descriptions identify:
   559→
   560→- Three.js
   561→- Custom shaders
   562→- Scroll animation
   563→- Parallax
   564→- 3D interaction design
   565→- Text splitting
   566→- Project-page Gaussian blur
   567→- A hidden footer interaction
   568→- A skills scroll section
   569→- Card and list views
   570→
   571→The key lesson is that the site does not make visitors choose between usefulness and experimentation. It offers a large, navigable archive while adding interactive material behavior.
   572→
   573→## 6.2 Strong typographic identity
   574→
   575→The portfolio uses highly distinctive display typography and a restrained black-and-white palette. The visual identity comes from type, spacing, and composition before effects are added.
   576→
   577→### Application to Y/G
   578→
   579→The Y/G redesign should define a strong type system:
   580→
   581→- Expressive display type for hero and major statements
   582→- Neutral, highly readable sans-serif for explanations
   583→- Technical mono for system labels and data
   584→
   585→The display type should feel engineered and human, not gothic unless that direction genuinely fits the Y/G brand.
   586→
   587→## 6.3 Service cards with real visual content
   588→
   589→Ryan’s services are paired with project imagery and direct benefit statements.
   590→
   591→### Application to Y/G
   592→
   593→Capabilities should include miniature real outputs:
   594→
   595→- Product strategy: flow map or product architecture
   596→- Experience design: interface states and user journey
   597→- AI implementation: model routing / memory / retrieval diagram
   598→- Full-stack delivery: deploy pipeline and live status
   599→
   600→This is stronger than four abstract icons.
   601→
   602→## 6.4 Card view and list view
   603→
   604→The ability to switch between card and list views is one of the most useful ideas in the reference set.
   605→
   606→### Why it works
   607→
   608→- Visual visitors can browse project imagery.
   609→- Technical or scanning-oriented visitors can compare metadata quickly.
   610→- It makes a large archive manageable.
   611→- It creates a functional interaction, not only decoration.
   612→
   613→### Application to Y/G
   614→
   615→Selected work on the homepage should remain cinematic, but an **All Systems** route could offer:
   616→
   617→- Cinematic card view
   618→- Compact systems list
   619→- Filter by product type
   620→- Filter by status
   621→- Filter by platform
   622→- Search by technology or capability
   623→
   624→This becomes more valuable as Yash’s portfolio grows.
   625→
   626→## 6.5 Custom shaders as material
   627→
   628→The portfolio’s project transitions use shader behavior such as Gaussian blur. This is important: the shader is not merely a decorative background. It changes how project media appears and transitions.
   629→
   630→### Application to Y/G
   631→
   632→Use shaders in specific, meaningful places:
   633→
   634→- Signal distortion during the opening
   635→- Project media displacement when transitioning between systems
   636→- Controlled blur or refraction when entering a case study
   637→- Soft memory-smear effect for B.R.A.C.E.
   638→- Knowledge-node energy field for Lernio
   639→
   640→Do not use one shader indiscriminately across the page.
   641→
   642→## 6.6 Text splitter
   643→
   644→Split text can make headings feel carefully choreographed. It is most effective when used on a few important transitions.
   645→
   646→### Application to Y/G
   647→
   648→Use split-line reveals for:
   649→
   650→- “A Human Signal Inside the Machine”
   651→- “Building Useful Futures”
   652→- Project titles
   653→- Final CTA
   654→
   655→Avoid animating every character in every paragraph.
   656→
   657→## 6.7 Hidden footer interaction
   658→
   659→A hidden footer creates a final reward for visitors who reach the end.
   660→
   661→### Application to Y/G
   662→
   663→The final scene can appear to complete the Signal Core, then reveal contact and footer information as the page slightly “opens” beneath the system frame. The footer should still be accessible without requiring a precise gesture.
   664→
   665→## 6.8 Project pages
   666→
   667→The reference distinguishes homepage spectacle from project-page explanation. The project route can use motion during entry, then become a readable case study.
   668→
   669→### Application to Y/G
   670→
   671→Case studies should be visually strong but quieter than the homepage. Use large media, strong diagrams, concise text, and occasional controlled motion. Do not run a full GPU-heavy hero behind the entire article.
   672→
   673→## 6.9 What Y/G should learn from Ryan
   674→
   675→Borrow:
   676→
   677→- Strong type-led identity
   678→- Functional card/list view switch
   679→- Large scalable project archive
   680→- Custom shader transitions
   681→- Project-specific motion
   682→- Hidden final reveal
   683→- Clear service information
   684→- Case-study routes with continuity
   685→
   686→Do not copy:
   687→
   688→- Blackletter type
   689→- Monochrome identity if it conflicts with Y/G
   690→- Exact blur shader
   691→- Exact project-card layout
   692→- Motion that hides essential information
   693→- Large archive density on the homepage

   697→# 7. Haoqi — Why one WebGL idea becomes unforgettable

   699→## 7.1 Core design idea
   700→
   701→Haoqi’s homepage behaves like a digital instrument. Public descriptions and visual previews show:
   702→
   703→- A deep cobalt environment
   704→- A fixed HUD grid
   705→- Live clock
